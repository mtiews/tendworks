# Tendworks – Implementation

This document describes the concrete technical implementation. Concepts, domains and contracts are covered in "Tendworks – Platform Architecture"; what the software factory is meant to do is in "Software Factory on Tendworks". This document covers only technology, code structure and operations.

**Name:** Tendworks (short: Tend) is the platform; domain `tendworks.dev`, `tendai.dev` redirects. The command line is called `tend` (e.g. `tend status`, `tend run list`). The software factory is an application on Tendworks and lives as configuration in its own repo, not in the platform code.

## Technology decisions

| Topic | Decision | Rationale |
| --- | --- | --- |
| Language | TypeScript throughout (Node.js LTS), TypeScript 6 for now | one language for services, UI and adapters; official SDKs for Temporal, A2A and MCP; ACP adapter for Claude Code is written in TypeScript; TypeScript 7 (native compiler) has no stable JS API yet, which code generators such as openapi-typescript need |
| Contracts in code | OpenAPI types generated with openapi-typescript into `packages/shared`, client via openapi-fetch, HTTP server on Hono | generated types keep server and clients on the contract; Hono serves a plain fetch handler, so the API can be tested in-process |
| Tests | Vitest; unit tests per package, end-to-end tests against the compose stack in `tests/e2e` | one runner for both levels |
| Repos | monorepo `tendworks` for code and contracts, separate repo `tendworks-config` for configuration | contracts change in the same pull request as the services; configuration has its own approvals |
| Package management | pnpm workspaces | fast, clean monorepo without an extra build system |
| Boundaries in code | one package per domain, cross-imports forbidden by lint rule (e.g. dependency-cruiser) | domain separation is checked automatically |
| Other languages | via spike behind the same interfaces | either side stays replaceable |
| CLI | tend in TypeScript on an API client generated from the OpenAPI contract; framework commander | same language as the rest; the generated client keeps the CLI from drifting away from the API; later shippable as a single binary; commander over oclif because plugins and auto-update are not needed |
| Harness adapter | Claude Code via `@agentclientprotocol/claude-agent-acp` (stdio), client side `@agentclientprotocol/sdk`; exact versions pinned | official ACP adapter; the ACP session id equals the Claude Code session id, so `session/resume` restores a session as long as the Claude config directory and the workspace survive on a volume; the adapter must run as non-root |

**Development approach:** Contract-first – contracts (OpenAPI, JSON Schema, event types) are written before the implementation, contract tests check each side. Test-driven development where it makes sense (interpreter, policies, adapters, action journal), not dogmatically for all code.

**Agent skills for development:** The `tendworks` repo uses Matt Pocock's skills ([mattpocock/skills](https://github.com/mattpocock/skills)).

- **Setup:** run `setup-matt-pocock-skills` once; issue tracker (GitHub), triage labels (including `ready-for-agent`) and the location of the domain docs are stored as Markdown under `docs/agents/`.
- **grill-me:** challenge a task before implementing it; a small-scale version of the factory's requirement validation.
- **tdd:** enforces red-green-refactor; the repo defines which packages it applies to (e.g. interpreter, policies, adapters, action journal), so TDD is not applied dogmatically to all code.
- **Versioning:** skills pinned to a fixed version, updates deliberately via pull request.
- **Dogfooding:** the existing issue agent can already contribute to the platform itself using these skills.

## Repo structure `tendworks` (first draft)

```text
tendworks/
  contracts/                 # contracts, language-neutral
    openapi/control-plane.yaml
    openapi/sandbox.yaml
    events/                  # CloudEvent types as JSON Schema
    schemas/                 # JSON Schemas per kind (Workflow, AgentProfile, ...)
  packages/
    control-plane/           # API, reads configuration from Git or a folder
    trigger-gateway/         # time triggers, webhooks later
    orchestration/           # Serverless Workflow interpreter on Temporal
    agent-runtime/           # A2A task model, ACP adapter, action journal
    sandbox/                 # sandbox API, backend Docker (runc, optionally gVisor)
    human-interaction/       # approvals, notifications
    event-bus/               # port + Postgres implementation
    mcp-platform/            # read-only MCP server on the control plane API
    shared/                  # only types generated from contracts/
    health/                  # platform library, not a domain: health probes and the runtime health API
    platform/                # platform library, not a domain: CloudEvent envelope and trace context, secret references, Server-Sent Events and following a transcript stream
  apps/
    server/                  # walking skeleton: bundles control-plane, trigger-gateway, human-interaction, mcp-platform
    worker/                  # walking skeleton: bundles orchestration, agent-runtime
    web/                     # web UI (SPA, served by the server under /ui/): status, runs, approvals, notifications, chats
    cli/                     # tend CLI on the generated API client
  images/
    sandbox-claude-code/     # Dockerfile: Claude Code + ACP adapter
  deploy/
    compose.yaml
    .env.example             # laptop profile settings and secrets, copied to deploy/.env
  tests/
    contract/
    e2e/
  docs/adr/
```

Packages under `packages/` map to the domains; apps under `apps/` are only bundles for operations and can be split later without moving code.

## Walking skeleton: build order (milestone 1)

Every slice ends with a working `docker compose up`. Configuration lives in `examples/config/` in this repo, which the control plane reads as a folder; the separate `tendworks-config` repo follows later.

| # | Slice | Proves |
| --- | --- | --- |
| S0 | Scaffold: pnpm workspaces, dependency-cruiser rules, Compose with Postgres and Temporal (dev mode), empty `server` and `worker`, `tend status` | repo structure, domain boundaries |
| S1 | `POST /runs` → minimal workflow interpreter (`do`, `call`) → A2A task → fake agent; `tend run list/get`; restart test for the workflow; durable agent tasks resumed after a restart (ADR 0004) | control plane contract, interpreter, A2A seam, generated client, durable execution |
| S2 | Fake agent replaced by Claude Code via ACP in a `container` sandbox (through the socket proxy); transcript and cost on a local volume; resume via `session/resume`; restart test for the agent session | sandbox API, ACP, agent runtime |
| S3 | Time trigger plus GitHub polling for `ready-for-agent` in the playground repo | trigger gateway, TriggerBinding, integration port |
| S4 | Pull request by the agent, merge as a workflow step behind `merge: auto \| ask`, event bus (Postgres outbox) with its first consumer, persisted notifications and approval requests, fake notification adapter | event bus, human interaction, milestone 1 success criterion |
| S5 | Hardening: contract tests, `gvisor` verified once on a Linux host | fitness functions, isolation opt-in |

Rules for the skeleton:

- **Fakes first.** Each seam gets its fake before its real adapter; the fake stays as the second implementation of the port.
- **Contracts only as far as used.** OpenAPI and JSON Schemas cover only what the current slice uses; types are always generated from them, never written by hand. Contract tests follow in S5 (ADR 0013 (contract-and-port-fitness-functions)): `tests/contract` checks the HTTP APIs and events against their contracts, `tests/architecture` checks product names and ports.
- **Interpreter grows with demand.** `listen` and `switch` are added when the merge gate needs them, test-driven.
- **Event bus with its first consumer.** The control plane reads runs synchronously through the orchestration API (`contracts/openapi/orchestration.yaml`, served by the worker). Run and step events go onto the event bus in the transaction of the run state (ADR 0003, ADR 0005); the first consumer is human interaction, which records a notification for every completed or failed run and every approval request before delivering it. Human interaction publishes `approval.requested` and `approval.decided` the same way; orchestration consumes every other domain's event that names a run and hands it to that run's `listen` tasks.
- **Resume is tested from S1 on**, not at the end.
- **Policies are YAML before they are Rego.** The architecture names Rego evaluated by OPA for policies; the skeleton has no OPA. Until it does, a policy is a configuration document `kind: Policy` (`contracts/schemas/policy.schema.yaml`, `spec.merge: auto | ask`, optionally `spec.workflows`), evaluated by a pure decision function `decide()` in human interaction (`allow | ask`, the strictest applicable policy wins). The function's signature is the seam a policy engine replaces later; the `kind: Policy` documents then become Rego modules with tests.

### Triggers: one firing per issue

A trigger binding starts at most one run per matching issue, also when that run fails, so a persistently failing issue never starts a paid run at every check (ADR 0006 (trigger-gateway-fires-once-per-issue-through-the-public-api)). To retry an issue, start the workflow by hand with the same input, e.g. `curl -X POST localhost:8080/runs -H "authorization: Bearer $TEND_API_TOKEN" -H 'content-type: application/json' -d '{"workflow":"develop-issue","input":{"issue":{...}}}'`; that run is recorded as started `manual`. `tend trigger list` shows each binding's last check (`LAST CHECK`): a check that could not ask its source (rate limit, API error, a secret that is not set) or could not start a run is `failed` with the reason. A suspended binding (`spec.suspend: true`) is never checked on its schedule.

## Claude Code harness

Agent profiles with `harness: claude-code` run Claude Code through `@agentclientprotocol/claude-agent-acp` (pinned in `images/sandbox-claude-code/package-lock.json`) in a sandbox from the profile's sandbox template. The agent runtime attaches to the adapter's stdio through the sandbox API, marks the harness onboarding complete and sets `bypassPermissions` in the session's config before it starts (for a profile with `attribution: false` also an empty `attribution` setting, so Claude Code adds no co-author trailers, generated-with lines or session links to commits and pull requests), records the ACP stream as product-neutral transcript entries and destroys the sandbox when the session ends (ADR 0007 (agent-runtime-records-transcripts-and-cost-from-acp), ADR 0017 (live-agent-output-streams-through-the-api-not-the-event-bus)).

The regular test suites use a scripted ACP agent behind the fake sandbox. The end-to-end suite runs the harness on the real path with a scripted ACP agent image instead of Claude Code (`images/sandbox-scripted-acp`, workflow `restart-scripted`): sandbox through the socket proxy, session volumes, ACP over the attached stdio, and `session/resume` in a new sandbox after a platform restart (`tests/e2e/restart-acp.test.ts`). `pnpm e2e` builds that image; the harness still needs a credential selected (`TEND_CLAUDE_CODE_CREDENTIAL=api-key` with any `ANTHROPIC_API_KEY` will do, as in CI), and the test is skipped without one. The real harness with Claude Code is a manual smoke test:

1. Build the sandbox image: `docker compose -f deploy/compose.yaml --profile sandbox-images build`.
2. In `deploy/.env` set `TEND_API_TOKEN` (`openssl rand -hex 32`; export it in your shell too, the `tend` CLI and the `curl` calls below send it, also for reading, which needs a token except `GET /status`) and `TEND_API_READ_TOKEN` (another `openssl rand -hex 32`; accepted for reading only) and `TEND_CLAUDE_CODE_CREDENTIAL=oauth-token` with `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`), or `TEND_CLAUDE_CODE_CREDENTIAL=api-key` with `ANTHROPIC_API_KEY`. Only the selected one enters the sandbox. Run steps 3 and 4 once with each credential kind (restart the worker after switching): both must complete, and the transcript must show the selected variable's value nowhere. The `developer` profile also passes the agent token in, so set `TENDWORKS_AGENT_GITHUB_TOKEN` (fine-grained, playground repository only, contents and pull requests read/write).
3. `docker compose -f deploy/compose.yaml up -d --build --wait`, then start the example: `curl -X POST localhost:8080/runs -H "authorization: Bearer $TEND_API_TOKEN" -H 'content-type: application/json' -d '{"workflow":"hello-developer"}'`.
4. `tend run get <id>` shows the run completed, the reply `hello from the sandbox`, a non-zero `COST` (an estimate with `oauth-token`, the billed amount with `api-key`; zero means the harness reported none, which is a failure of this test) and the transcript reference; read the transcript with `tend run logs <id>` (through the API, like every client). With `<task>` the step's `taskId` (`tend run get <id> -o yaml`), `docker ps -a --filter volume=tendworks-volume-<task>-session` lists no leftover sandbox and `docker volume ls --filter name=tendworks-volume-<task>-` no leftover volume (the scripts check only their own tasks, so debris of integration test runs on the same Docker daemon does not count).

The workspace (`/workspace`) and the harness's home and config directory (`/session`) are volumes of the agent session, and the ACP session id is kept with the task, so after a platform restart the harness resumes the session with `session/resume` in a new sandbox (ADR 0009 (agent-sessions-resume-on-their-volumes)). Manual restart smoke test with the real harness, after steps 1–3:

5. Run steps 5–7 automatically with `scripts/smoke/restart-developer.sh` (Git Bash; prints PASS or FAIL), or by hand: start `curl -X POST localhost:8080/runs -H "authorization: Bearer $TEND_API_TOKEN" -H 'content-type: application/json' -d '{"workflow":"restart-developer"}'` and wait until `tend run get <id>` shows the step running and `tend run logs <id>` shows a `session-started` entry (the agent created `before.txt` and sleeps).
6. `docker compose -f deploy/compose.yaml restart worker`.
7. Within about a minute (the engine's heartbeat timeout) the transcript (`tend run logs <id> -o yaml` shows the entry types) shows `task-resumed` and `session-resumed` with the same session id, not `session-resume-failed`. The run completes with `resumed: 1` and a reply listing `after.txt` and `before.txt`; no sandbox or volume is left over.

### Transcripts and live output

A running step names its task and transcript as soon as the agent runtime created the task; the control plane reads the transcript through the agent runtime API (`contracts/openapi/agent-runtime.yaml`, served by the worker), and `tend run logs <id>` prints it. The agent runtime API also serves a transcript live as Server-Sent Events (`GET /tasks/{taskId}/transcript/stream`: one `entry` event per entry with its position as event id, then `end` when the task ends); the control plane passes the stream through unchanged (`GET /runs/{runId}/tasks/{taskId}/transcript/stream`), a client that reconnects with `Last-Event-ID` continues right after that entry, and `tend run logs <id> --follow` streams the steps of a run one after another until the run ends. Live entries come from the worker process that runs the task (in memory, nothing on the event bus); with one worker that is enough (ADR 0017 consequence), and its connections are cut on shutdown so clients reconnect.

### Chats

Chats (ADR 0015 (a-chat-is-an-a2a-task-without-a-run)) use the same harness and transcripts. A profile with `spec.chat` can be chatted with through `POST /chats` (agent runtime API and control plane alike, plus `GET /chats`, `GET /chats/{chatId}`, `POST /chats/{chatId}/messages`, `POST /chats/{chatId}/cancel`, `POST /chats/{chatId}/end` and the chat's transcript and stream). The chat is one A2A task (kind `chat` in `agent_runtime.tasks`) that waits in `input-required` between turns, each turn is one more prompt in the same ACP session, the sandbox stays between turns until the profile's `spec.chat.idleMinutes` pass without a message, then it is destroyed and the volumes stay. The next message resumes the session (`session/resume`) in a new sandbox, as after a restart, and the transcript shows `session-resumed`. On start the worker takes up the chats that have not ended (`AgentRuntime.resumeChats`): a turn a restart interrupted continues in the resumed session (with a `task-resumed` entry), and waiting chats lose their sandbox when their idle time is over. Ending a chat removes sandbox and volumes. A message during a turn is refused with 409; cancelling the turn instead sends ACP `session/cancel` and answers once the turn stopped (`turn-ended` with reason `cancelled`), with the chat waiting for the next message; an agent that does not stop within a grace period loses its harness process, and the next turn resumes the session in a new sandbox. The transcript marks each turn's end with an `input-required` entry and each further message with `message-received`. `chat.started` and `chat.ended` go onto the event bus in the transaction of the task. A chat keeps the harness of its profile, so a chat whose profile was removed from the configuration can still be ended: `POST /chats/{chatId}/end` removes its sandbox and volumes from what was kept of its session, and on start the worker fails such a chat (`agent profile <name> is no longer configured`) and cleans up the same way.

### Chat CLI

`tend chat <profile>` sends the lines the operator types and streams the agent's output; `tend chat attach <id>` prints a chat's history and continues it the same way, from any number of clients at once (each sees every entry, any of them can send the next message). Ctrl+C cancels a running turn and leaves the chat open while the agent waits; `/end` ends the chat, end of input leaves it open. `tend chat list`, `tend chat get <id>` (both with `-o yaml|json`) and `tend chat end <id>` complete the set. `tend chat <profile> --repo <url>` (the `repository` field of `POST /chats`) starts the chat with a public repository checked out as its workspace: the first message carries it as task workspace without a branch (ADR 0010), the checkout runs without a token before the first turn and stays on the repository's default branch; the agent runtime refuses anything but an `https`/`http` URL without user name or password with 400, and a checkout that fails fails the chat with git's reason. A chat without a repository starts with an empty workspace.

### Agent sessions

Who works right now comes from the agent runtime: `GET /sessions` of the agent runtime API lists the agent sessions whose task has not ended (from `agent_runtime.tasks`, partial index on non-terminal tasks), kind `run-step` with the run and step the step's `SendMessageRequest.metadata` named (kept in the task's metadata), or kind `chat`. `GET /agents` of the control plane puts them under their profile (`sessions`, schema `contracts/schemas/agent-session.schema.yaml`) and lists the profiles without `sessions` when the agent runtime cannot be reached; `tend agent list` shows their number (`?` while unknown), `-o json|yaml` the sessions. Each profile also carries its `chat` settings (absent: no chats) and the `mcp` servers it lists, so clients offer chats only with profiles that allow them.

### Platform MCP server

Chat agents read the platform through the platform MCP server (ADR 0016 (chat-agents-read-the-platform-through-mcp-with-a-read-only-token), `packages/mcp-platform`, official MCP TypeScript SDK): the server bundle serves it at `/mcp` on the API's port over Streamable HTTP (stateless, JSON responses) with the read-only tools `list_runs` (newest first, `limit` default 20), `get_run`, `list_triggers` and `list_agents`. It is a client of the public control plane API (in process, generated client) with the bearer token its caller presented; a request without a token, or with one the control plane refuses, gets 401 and nothing else, not even the list of tools. A profile lists it with `spec.mcp: [tendworks]` (the example `assistant` does, `developer` does not); for sessions of such profiles, chats and workflow tasks alike, and only those, the Claude Code harness configures it in ACP `session/new` and `session/resume` (`mcpServers`, HTTP, with an `Authorization: Bearer` header holding the read-only token), never through the sandbox's environment, and redacts the token from transcripts and replies. A session of such a profile fails with a hint when the worker has no `TEND_PLATFORM_MCP_URL` or `TEND_API_READ_TOKEN`, or when the harness does not advertise MCP over HTTP; the server refuses to start without a valid `TEND_API_READ_TOKEN` when a profile lists it.

`TEND_PLATFORM_MCP_URL` is the address sandboxes reach the server's published port at: compose defaults it to `http://host.docker.internal:${TEND_PORT}/mcp`, which works on Docker Desktop. On Linux there is no working default yet: sandboxes do not resolve `host.docker.internal`, and even through the sandbox network's gateway they cannot reach the port, since compose publishes it on `127.0.0.1` only (open item).

### Residual risk: sandboxes reach the API's port

Sandboxes run on their own network without the platform's services, but every sandbox still reaches the control plane's published port wherever the Docker host forwards it to them (on Docker Desktop through `host.docker.internal`). Until the egress proxy closes that path, the bearer tokens are the guard, not the network (ADR 0014 (interim-bearer-token-on-the-control-plane-api), ADR 0016): no sandbox holds the API token, so none can change state, and only sessions of profiles that list the platform MCP server hold the read-only token, so only they can read.

### Web UI

`apps/web` is a React + Vite single-page application (ADR 0018 (the-web-ui-is-a-same-origin-spa-signed-in-with-an-api-token)). The control plane handler serves its build under `/ui/` without a token (option `webUi: { root }`; `packages/control-plane/src/web-ui.ts`): `GET /` and `/ui` redirect to `/ui/`, files under `/ui/assets/` (hashed by Vite) are cached for good, the entry page and other files are revalidated (`no-cache`), any other path under `/ui/` gets the entry page so client-side routes work as deep links, and a missing asset gets 404. Every answer under `/ui/` carries a strict Content Security Policy (`default-src 'none'`; scripts, styles, images, fonts and connections from the origin only; no framing, no form posting, no `<base>`), `nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer`; so the app has no inline script or style (no `style=` attributes in markup, Vite's module preload polyfill off, assets never inlined as `data:` URLs). The server bundle finds the build at `apps/web/dist` next to its own `dist` (override with `TEND_WEB_UI_DIR`) and serves 404 under `/ui/` when there is none.

- **Build**: `pnpm build` type-checks the app and runs `vite build`; the server image contains the build, so `docker compose up` serves the UI at `http://localhost:8080/` with no extra step.
- **Dev server**: start the stack (`docker compose -f deploy/compose.yaml up -d`), then `pnpm --filter @tendworks/web dev` serves the app with fast reloads at `http://localhost:5173/ui/` and proxies every path outside `/ui/` (the API, streams included) to `TEND_URL` (default `http://localhost:8080`). The dev server sends no CSP; the browser tests check it against the real server.
- **Sign-in and access**: the app asks for an API token, checks it with `GET /access` (`{ scope: "read" | "full" }`) and keeps it in `sessionStorage`, or `localStorage` with "Stay signed in on this device"; sign-out removes it. Every request goes through the client generated from the contract (`openapi-fetch` over `ControlPlane.paths`) with the token as bearer token; any 401 returns to sign-in, and each navigation asks `GET /access` again so a token that is no longer accepted is noticed on any page. `tend status` shows the token's access as `ACCESS full|read|none` (table only; `-o json|yaml` stays the status document).
- **Code layout**: `src/app.tsx` (sign-in state), `src/api.tsx` (client, `useApi()` with `client` and `scope`), `src/router.tsx` (small History API router under `/ui`, `Link`, `match`), `src/routes.tsx` (the views and their paths; view tickets replace their placeholder there), `src/shell.tsx` (navigation, access, sign-out), `src/styles.css` (design tokens as CSS custom properties, light/dark from the system, phone-width layout: below 40rem the navigation wraps into a grid of three entries per row under the brand, access scope and sign-out, with touch targets at least 44px high and nothing scrolling sideways). `src/index.ts` exports `App` for the entry point and the view tests. Read-only mode: views read `useApi().scope` and offer no action for `read`.
- **Lists poll**: `usePolling(load)` (`src/use-polling.ts`) calls `load` at once and 5 seconds after each answer, stops while `document.hidden` and polls at once when the tab shows again; it gives `{ data, error, loading, refresh }` (`refresh()` polls at once, e.g. after an action) and keeps the last data while a poll fails. Keep `load` stable with `useCallback`. Shared view pieces: `Time` (`src/time.tsx`, locale time with the exact timestamp in `dateTime`) and `Pending` (`src/pending.tsx`, loading or "Cannot read the …"). The status page (`src/status.tsx`) polls `/status`, `/runs`, `/agents` and `/triggers` per section, so one unreachable part does not blank the rest; sessions show as `unknown` when `GET /agents` leaves `sessions` out.
- **Runs**: `src/runs.tsx` (list, polling `/runs`) and `src/run-detail.tsx` (`/runs/:runId`: summary, a failed run's error as an alert, steps with cost, output like `tend run get`, and per agent step its transcript: the history from `GET /runs/{runId}/tasks/{taskId}/transcript`, then, while the step runs, live from its stream, marked "Live"; the stream's end reads the run again at once (`usePolling`'s `refresh`), so the step's end shows without a reload, and the transcript is read again). `answer(call)` (`src/answers.ts`) turns a client call into its data or an error the operator can read (`AnswerError` with `status`, or "Cannot reach the platform").
- **Live transcripts**: `followTranscript` of `@tendworks/platform` (browser-safe, used by `tend` and the web app) follows a transcript stream after a given position, resumes a dropped connection with `Last-Event-ID` after the last entry it handed over and skips any entry at or before it, so nothing is missing or shown twice; it gives up after 5 failed connections in a row (1 s apart). In the app, `useTranscript({ read, open, live, onEnded? })` (`src/use-transcript.ts`) reads the history, then follows the stream after its last entry while `live`; `<LiveTranscript>` (`src/live-transcript.tsx`) renders it with the transcript renderer and says when it is loading, missing, empty, live or lost. Run steps and chats use both alike. The stream request gets no abort signal (jsdom's would be refused by `Request` in the view tests); stopping cancels the body instead.
- **Approval requests**: `src/approvals.tsx` (`/approval-requests`, polling `GET /approval-requests`: pending first, then decided ones with their decision; age, question, action and policy, run link) and `src/run-approval.tsx` (on the run detail: the run's pending request, polling `GET /approval-requests?status=pending`, nothing when there is none). Both decide through `DecisionActions`: approve and reject each open a confirmation that repeats the question; a refused decision (409 when decided the other way elsewhere) shows as an alert and the list is read again at once (`usePolling`'s `refresh`). Read-only access shows the requests without actions. Requests decided elsewhere (`tend`, another tab) show as decided with the next poll.
- **Chats**: `src/chats.tsx` (`/chats`, polling `GET /chats`: profile, status, start, last activity, cost; "New chat" for full access), `src/new-chat.tsx` (`/chats/new`: the profiles with `chat` in `GET /agents`, the first message and an optional public repository; a refused start shows the problem's title and detail, e.g. an invalid repository) and `src/chat-window.tsx` (`/chats/:chatId`: the chat's summary with its total cost, polling `GET /chats/{chatId}`, and the conversation: history, then live while the chat is open, through `useTranscript` and `TranscriptOf`). Whether the agent waits is read from the transcript, which arrives live while the polled chat lags (`turnOf`: the last `input-required`, `task-ended` or turn-starting entry decides); a turn that starts or ends reads the chat again at once. The input is enabled only while the agent waits and stays disabled after sending until the transcript moves past that point; Send, Enter or Ctrl+Enter (Cmd+Enter) sends under the same rules as the button and Shift+Enter is a new line; the Enter that ends an input method's composition (`isComposing`, key code 229) never sends; on touch screens (`(pointer: coarse)`, whose keyboards have no Shift) Enter stays a new line, only the button sends, and the hint "Enter to send · Shift+Enter for a new line" next to Send (the input's `aria-describedby`) is left out; a refused message (409) shows the platform's reason. While the agent works, "Cancel turn" (`POST /chats/{chatId}/cancel`) stops the turn; the transcript's `turn-ended` and `input-required` reopen the input. "End chat" asks with a `Confirmation`; a chat ended elsewhere loses its input as soon as the transcript shows `task-ended`, before the chat is read again. Several tabs or devices on one chat behave like several `tend chat attach` clients: all state is on the platform, each sees every entry and any of them can send, cancel or end. Each wait for the next message shows the turn's cost and the total (`input-required` carries the running total; the renderer subtracts the previous one). The input and its buttons stick to the bottom of the viewport (CSS `position: sticky`); `useFollowEnd` (`src/use-follow-end.ts`) opens the window at the end of the history, goes to the end after sending, and follows new entries only while the operator is within 80px of the end, so whoever scrolled up to read stays there; scrolling is smooth unless the operator prefers reduced motion. Read-only access shows chats and follows them live, without new chat, input or end.
- **Confirmation**: `<Confirmation title confirmLabel onConfirm onCancel busy>` (`src/confirm.tsx`) asks before an action: an inline, non-modal `alertdialog` (no `<dialog>` element, no inline style) named by its title and described by its children. It focuses Cancel; Cancel and Escape close it and return the focus to the element that opened it; `busy` disables both choices while the action runs.
- **Transcript renderer**: `<Transcript entries={...} />` (`src/transcript.tsx`) renders the entries it is given, in order, so a live stream appends to the array: consecutive message chunks join into one message rendered as Markdown, tool calls are rows (title, kind, status) that expand to their output, thoughts and harness output show only behind the "Show thoughts" / "Show harness output" toggles, turn ends carry the cost so far (from `usage`), each wait for the next message (`input-required`) the cost of the turn before it and the total, resumes are markers. Items keep their keys (position of their first entry), so expanded rows stay expanded while entries arrive. Agent Markdown (`src/markdown.tsx`) goes through `marked` with raw HTML escaped, images rendered as `[image: alt]` text and only http(s)/mailto links, then through DOMPurify with an allowlist of plain Markdown elements; links open in a new tab with `noopener noreferrer`. Use `safeHref(url)` for any other link an agent reported (artifacts).
- **Import rule**: the app may import only `@tendworks/shared`, the platform libraries and npm packages, never a domain, another app or a Node.js module (dependency-cruiser `web-app-is-a-client`).
- **View tests** (`tests/web`, Vitest project `web`, jsdom; part of `pnpm check` and `pnpm coverage`): render the whole `App` with `renderApp({ path, ...controlPlaneOptions })` from `tests/web/support/platform.tsx`, whose `fetch` is the real `createControlPlaneApi` over in-memory fakes (pass `agentRuntime`, `runs`, `approvals`, `notifications`, `triggers` like the control plane's own tests). It returns Testing Library's `user`, and `platform` with the requests the app sent, `restart(options)` (e.g. other tokens) and `unreachable(down)`. Tests query what the operator sees (roles, labels, text). They live outside `apps/web` so its import rule holds; `nothing-imports-apps` lets only `tests/web` import `apps/web`.
- **Browser tests** (`tests/browser`, Playwright, `*.spec.ts`): run against the compose stack at `TEND_URL` at desktop and phone width (Pixel 7), each failing on a CSP violation or page error (`support/test.ts`). `pnpm e2e` runs them after the API end-to-end tests; `pnpm e2e:browser` runs only them against a running stack. Locally they need Chromium once: `pnpm --filter @tendworks/browser-tests exec playwright install chromium`.

### Pull request smoke test

The `develop-issue` workflow hands an issue to the `developer` agent. The runtime checks the issue's repository out in the workspace on a branch fixed by the run, copies the profile's skills into the sandbox, passes the agent token in as `GH_TOKEN` and appends the role description to the harness's system prompt; the agent pushes the branch, opens the pull request and records it, so the run's output shows it (ADR 0010 (agent-runtime-prepares-the-workspace-and-collects-reported-artifacts)). The regular suites cover this with the scripted agent and a local bare repository; against the playground repository, after steps 1–3:

8. Open an issue in `mtiews/tendworks-playground` with a small, clear change, e.g. "Add a file GREETING.md that says hello".
9. Start a run for it by hand: `curl -X POST localhost:8080/runs -H "authorization: Bearer $TEND_API_TOKEN" -H 'content-type: application/json' -d '{"workflow":"develop-issue","input":{"issue":{"repository":"mtiews/tendworks-playground","number":<n>,"title":"<title>","body":"<body>","url":"https://github.com/mtiews/tendworks-playground/issues/<n>"}}}'`. The run's `STARTED BY` names the binding and the issue.

10. `tend run get <id>` shows the run completed, with `pullRequest` and `branch` (`tendworks/issue-<n>-<first 8 characters of the run id>`) under OUTPUT. The pull request on GitHub comes from that branch, describes the change and references the issue. 12. In step 10, `tend run get <id>` additionally shows the `merge` step completed and `merged: true` and the merge `commit` under OUTPUT; on GitHub the pull request is merged by the platform token's owner, not by the agent. The server log names no token.
13. Failure: run `develop-issue` for an issue the agent cannot finish, or set the token to an invalid value and restart the server. The run fails at `/do/1/merge` with a readable title and detail (e.g. "No pull request to merge", "Repository unavailable: GitHub answered 401: Bad credentials ..."); nothing is merged.

## Schema migrations

Every domain owns a Postgres schema (`orchestration`, `agent_runtime`, `event_bus`, `human_interaction`, `trigger_gateway`) and migrates it itself with the platform library `@tendworks/platform/migrations` (a subpath export, so the browser-safe entry point the web UI imports never pulls in a database client).

- **Version table:** each schema has its own `<schema>.schema_migrations` (version, name, applied at). No domain reads another's.
- **On start:** each bundle migrates the domains it runs (worker: orchestration, agent runtime, event bus; server: event bus, human interaction, trigger gateway; the event bus is migrated by both, which the lock makes safe). Under the domain's advisory lock (`hashtext('<schema>.migrate')`), every migration above the recorded version runs in its own transaction together with its row in the version table, so concurrent starts migrate once.
- **Migration 1** is the schema as the stores created it before versioned migrations, with its `create … if not exists` and `alter … add column if not exists` statements. It adopts such a store with its data.
- **Failure:** a failed migration is rolled back, so the store stays at the version before it. The bundle logs `schema <schema>: migration <n> (<name>) failed: <error>` and stops working: the server answers only `GET /status`, the worker only `GET /health` (every other request gets 503), and both report the component `<schema>-schema` (e.g. `orchestration-schema`) as unhealthy, so `GET /status` shows it either way. A store at a newer version than the release knows fails the same way (no downgrades). The next start tries again.

To add a migration to a domain:

1. Append an entry to the domain's list in its Postgres adapter (e.g. `orchestrationMigrations` in `packages/orchestration/src/adapters/postgres-run-store.ts`) with the next `version`, a short stable `name` and its `sql`. Never edit or reorder a released migration; versions count up from 1 without gaps.
2. Write the SQL for the store at the previous version. It need not be idempotent (the version table guards it), and it may use the domain's own tables only.
3. Extend the adapter's integration test (`*.integration.test.ts`), which migrates a fresh store and adopts one created by migration 1 with its data; add data the new migration must carry over.
4. Name the migration in the release notes.
