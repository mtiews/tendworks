# The merge gate decides by the run, and runs wait for approval requests with listen

The merge request no longer names a policy. `POST /pull-requests/merge { run, pullRequest }` names only the run and the pull request; the gate takes everything it decides by from the platform's own records: orchestration's record of the run (it must be running and must have reported the pull request as a `pull-request` artifact of one of its steps, which orchestration now records per step), the policies that apply to the run's workflow (`spec.workflows`, none means all; the strictest decision wins; none applying refuses the merge), and with `ask` the approval request for exactly this run, action and pull request. A caller that reaches the API, e.g. an agent in a sandbox, can therefore neither pick a lax policy nor merge another run's or an unreported pull request; at most it opens the same approval request the workflow would. This supersedes the request shape and the "workflows name the policy" rule of ADR 0011 (the-platform-merges-through-a-gate-on-the-control-plane-api).

With `ask` the first merge request opens the approval request (persisted by human interaction, `approval.requested` on the event bus in the same transaction, a notification recorded from that event) and answers 202. The workflow waits with the DSL's own means, `switch` and `listen` on `dev.tendworks.approval.decided`, and asks again once approved; the gate then finds the approved request and merges, or refuses with 403 after a rejection, which the workflow avoids by ending the run without a merge. Orchestration subscribes to the event bus and hands every other domain's event that carries a `runid` to that run (a signal of the durable engine, so the event is part of the run's history and survives restarts; events that arrive before the run listens wait in its inbox).

## Considered Options

- **Policy name in the request, validated against the run's workflow definition**: keeps the workflow naming its policy, but the gate would have to find the merge step in the definition and trust its literal; and a policy is about what the platform allows, not something a workflow author picks case by case (architecture: "whether one is created is decided by a policy, not by the workflow author").
- **Policies select workflows** (chosen), strictest wins: adding a policy can only make a gate stricter, and a typo in `workflows` is a configuration error rather than a silently skipped gate.
- **Shared secret between worker and server on the merge endpoint**: not needed for the gate's integrity once the decision rests on the platform's records, and it would not protect the decision endpoint, which a human client must reach anyway.
- **Gate opens the request, a separate endpoint merges an approved one**: two endpoints with the same checks; repeating the one idempotent merge request is simpler for workflows and retries.
- **Workflow polls the approval request instead of `listen`**: needs `wait` and a loop, and burns history; `listen` is the DSL's way to wait for an event and what the architecture names for approvals.

## Consequences

- Residual risk: the control plane API has no authentication yet (identity is a later milestone). Whoever reaches it can answer approval requests, including an agent in a sandbox where the published port is reachable from containers (Docker Desktop forwards `host.docker.internal` to the host's localhost). The gate stops agents from choosing their policy or merging unreported pull requests, but not from approving their own request; together with the agent token's ability to merge directly (ADR 0010 (agent-runtime-prepares-the-workspace-and-collects-reported-artifacts)), `ask` is a safeguard against mistakes, not yet a security boundary against a hostile agent. Closing it needs authenticated decisions (OIDC) and an egress allowlist for sandboxes.
- An agent can report any pull request URL as its artifact; the gate checks that the run reported it, not that it belongs to the issue's repository. With `auto` a hostile agent could get another pull request the platform token can merge merged; scope the platform token to the playground repository.
- The run's step records now carry `artifacts` (name, URL); the run snapshot of the workflow and the policies read at server start decide, so a policy change takes effect for merges after a server restart, also for runs already waiting.
- Approval events start their own trace: human interaction does not know the run's `traceparent`.
- A `listen` task only supports `to.one` with an event type; correlation is by `runid`, so a run waits for one approval at a time. Loops that call the same agent task again (`then` back to an `a2a` call) get the existing task, because the message id is derived from run and step.
