# The agent runtime prepares the agent's workspace and collects the results it reports

For the developer agent to open a pull request for an issue, four things reach the sandbox before the session starts, all generic and all driven by configuration:

- **Task input**: the workflow builds the message (issue title, body, link) like any other A2A message. The agent profile's Markdown body, the role description, is appended to the harness's system prompt (`session/new` and `session/resume` `_meta.systemPrompt.append` of the Claude Code adapter), followed by a short platform note on how to report results.
- **Workspace**: the message that starts a task may carry `metadata["dev.tendworks/workspace"] = { name, branch }` (`contracts/schemas/a2a.schema.yaml#/$defs/workspace`): a workspace configured by name (ADR 0022 (workspaces-are-declared-once-with-their-own-credentials)); an unknown name fails the task. The runtime prepares it through the workspace port; for a git workspace it runs a fixed checkout script in `/workspace` through the sandbox API's `exec`: clone if the workspace is not a checkout yet, then continue the branch if the remote has it, otherwise start it from the workspace's default branch. The example workflow `develop-issue` takes the workspace from its input and derives the branch from issue number and run id, so a retry of the step, a resumed session (ADR 0009 (agent-sessions-resume-on-their-volumes), the checkout lives on the workspace volume) and a re-sent task all work on the same branch and pull request. Without `branch` the checkout stays on the default branch. A chat (ADR 0015 (a-chat-is-an-a2a-task-without-a-run)) with a workspace's assistant prepares the workspace the same way before its first turn and again in every new sandbox, where the script keeps the checkout on the workspace volume as it is: read-only on the default branch, or with `write: true` on the chat's branch `tendworks/chat-<id>`.
- **Skills**: `spec.skills` names directories under `skills/` of the configuration folder; every file is copied into `$CLAUDE_CONFIG_DIR/skills/<name>/`, where the harness loads user skills. A missing skill fails validation at startup.
- **Secrets**: a git workspace's credential and a profile's `spec.env` are secret references (ADR 0008 (secret-references-resolve-against-the-platform-environment)), resolved against the worker's environment and, in the compose stack, the agent secrets of `deploy/.env` (ADR 0008), but only variables named `TENDWORKS_AGENT_*`. The workspace's credential reaches git through the image's generic credential helper (`git-credential-tendworks`), which the checkout configures for the repository's host only, and the session sees it under the name the workspace sets in `credentials.env` (the playground workspace: `GH_TOKEN`, for `gh`). Profiles carry no repository credential. The issues token, a platform secret, is not in the worker's environment (checked by `tests/architecture/secrets.test.ts`) and could not be resolved even if it were. A missing secret fails the task naming the secret; resolved values are redacted from transcripts and messages.

Results come back as A2A artifacts: the agent writes a JSON array of `{ name, url, description? }` to `/session/artifacts.json` (`$TENDWORKS_ARTIFACTS`); after a completed turn the runtime turns each entry into an artifact with one `url` part. The developer reports `pull-request`; the workflow's `output.as` puts its URL into the run's output, which `tend run get` shows.

## Considered Options

- **The agent clones the repository itself, told by the prompt**: no platform code, but the checkout and the branch rule would depend on the model following instructions, and a retry could start a second branch.
- **The platform opens the pull request after the session (push and API call with the agent token)**: deterministic, but puts a GitHub-specific step into the agent runtime; the spec has the agent open it (`git push`, `gh pr create`), and the human merges in the forge (ADR 0024 (the-platform-has-no-pull-request-integration)).
- **Parse the pull request URL out of the agent's final answer** (jq `capture` in `output.as`): no platform code, but the final answer is free text; the artifacts file is structured, harness-neutral and reusable for other results.
- **Pass the platform's whole environment to secret references**: simpler, but a profile could name the issues token or the database URL; the prefix makes "only agent secrets enter a sandbox" a property of the code, not of review.

## Consequences

- The agent token can still merge (accepted risk until a GitHub App token per run, see #2); the role description tells the agent never to merge. How far token permissions and a ruleset reduce this before then: [GitHub access for agents](../github-agent-access.md).
- `gh` is pinned with its checksum in the sandbox image (`images/sandbox-claude-code`), which also carries the credential helper; the image tag has a revision suffix (`0.85.1-2`), bumped with every change of the image, so it must be rebuilt.
- Reporting a result depends on the agent writing the file; a run whose agent reported no pull request completes with `pullRequest: null`; the branch is in the run's output too.
- A task needs only the secrets of its profile and its workspace: smoke tests without a workspace (`hello-developer`) need no repository token.
