# Tendworks v0.2.0 – clean single-host deployment on Linux

Milestone 2 (spec #54): Tendworks installs from a release tag on Ubuntu 24.04 with Docker Engine and runs there unattended. The first tagged release; it updates installations of the milestone 1c state (`main` before milestone 2). Follow [docs/operator-guide.md](../operator-guide.md).

## Before you update

- **Leftovers from before v0.2.0 stay until you remove them.** Before v0.2.0 every stack named its sandboxes and session volumes `tendworks-sandbox-*` and `tendworks-volume-*`, without an installation label, so the name alone cannot tell one stack's from another's. The new clean-up never removes such unlabelled resources; open chats of the installation `tendworks` still resume on their volumes. Once every older stack on the engine is stopped or updated, review and remove the rest by hand (operator guide, Reset).
- **With another `COMPOSE_PROJECT_NAME`** than `tendworks`: end open chats before the update. Afterwards their old volumes are no longer found, the chats start over with an empty workspace, and the old `tendworks-volume-*` volumes stay behind (operator guide, Reset).
- **Downgrades are not supported.** The way back is the backup taken in the update steps.

## Update steps

1. Stop the stack from the old checkout: `docker compose -f deploy/compose.yaml stop`.
2. `git fetch --tags && git checkout v0.2.0`
3. Bring `deploy/.env` up to date (compare with `deploy/.env.example`):
   - `TEND_API_TOKEN` and `TEND_API_READ_TOKEN` must be set, at least 16 characters, different from each other (`openssl rand -hex 32`). There are no default tokens any more.
   - `TEND_POSTGRES_PASSWORD` must be set; there is no default password any more. The store keeps the password it was created with: if you never set one, set `TEND_POSTGRES_PASSWORD=tend`, or change it with `ALTER USER` first (operator guide, Rotation).
   - Remove `TEND_PLATFORM_MCP_URL`, in particular a `host.docker.internal` value.
4. Back up with the new script: `scripts/backup.sh --output-dir <dir>`. The stack is stopped, so the script starts only the store for the dump and stops it again.
5. Point `TEND_CONFIG_PATH` at your own configuration (a copy of the new `examples/config`), unless you want the starter. In your own sandbox templates, name `tendworks/sandbox-claude-code` without a tag, so the pin in `deploy/compose.yaml` applies.
6. `docker compose -f deploy/compose.yaml --profile sandbox-images build`, then `docker compose -f deploy/compose.yaml up -d --build --wait`.
7. `tend status` is healthy and lists `sandbox-cleanup`; the logs show `store <domain>: migrated from version 0 to 1` for each domain.

## Migrations

Each domain now versions its schema in its own table `<schema>.schema_migrations`. This release has one migration per domain:

| Schema | Migration | What it does |
| --- | --- | --- |
| `orchestration` | 1 `initial` | the schema as before; adopts an existing store with its data |
| `agent_runtime` | 1 `initial` | as above |
| `event_bus` | 1 `initial` | as above |
| `human_interaction` | 1 `initial` | as above |
| `trigger_gateway` | 1 `initial` | as above |

A failed migration is rolled back. The bundle then keeps running but stops working (ADR 0021): the server answers only `GET /status` (every other path 503 `Platform stopped`), the worker only `/health` (every other path 503 `Worker stopped`), and `/status` shows the component `<schema>-schema` (e.g. `orchestration-schema`) unhealthy with the error. A store newer than the release fails the same way. The other bundle keeps running; the way back is the backup.

## Services, volumes and networks

| What | Change |
| --- | --- |
| `agent-secrets` | new one-shot service: writes the `TENDWORKS_AGENT_*` lines of `deploy/.env` for the worker and ends. `Exited (0)` is normal |
| `mcp-gateway` | new: forwards only `/mcp` to the server (ADR 0019); pinned reverse proxy image |
| `temporal-ui` | new, only in the compose profile `debug`. `temporal` runs headless and publishes nothing |
| restart policy | `unless-stopped` on every long-running service: the stack comes back after a reboot |
| volume `<installation>_agent-secrets` | new; holds the agent secrets as a file until the next `up` or `down -v` |
| network `<installation>_platform-mcp` | new, internal; the gateway and sandboxes of profiles with `mcp: [tendworks]` |
| sandboxes, session volumes, sandbox network | named `<installation>-sandbox-<id>`, `<installation>-volume-<name>`, `<installation>-sandboxes` with the label `dev.tendworks.installation`; the installation is the compose project name. Unchanged names for the default `tendworks`, so open chats resume |

## Changed defaults and configuration

- **No default tokens or store password.** The server refuses to start without `TEND_API_TOKEN` and `TEND_API_READ_TOKEN`, server and worker without `TEND_POSTGRES_PASSWORD`, and each names the variable to set. `scripts/setup-env.sh` creates `deploy/.env` with random tokens and a random store password, mode 600, and never overwrites one. `TEND_DATABASE_URL` no longer carries the password; the bundles encode it into their connection.
- **`TEND_PLATFORM_MCP_URL`** defaults to the gateway (`http://mcp-gateway:8080/mcp`) on Linux and Docker Desktop alike. Remove any override, in particular `host.docker.internal`.
- **Agent secrets** come only from `deploy/.env`: every `TENDWORKS_AGENT_*` line reaches the worker without a compose edit. Variables exported in the shell or given with `--env-file` no longer reach the worker. `TEND_SANDBOX_NETWORK` is gone.
- **Starter configuration.** `examples/config` holds no fakes any more (they moved to `tests/fixtures/config`): agents `assistant` and `developer`, workflows `develop-issue`, `hello-developer`, `restart-developer`, the suspended binding `playground-ready-for-agent`. A fresh stack starts no run.
- **`ask-before-merge`** now applies to `develop-issue`: the starter asks before merging the developer's pull requests. Remove it there for `merge: auto` (`scripts/smoke/pull-request-auto.sh` needs that).
- **Hidden directories** (`.git`, `.github`) in the configuration directory are skipped, so a configuration repository can carry its own CI.
- **Sandbox image pin** in one place, `x-sandbox-images` in `deploy/compose.yaml`. Templates name the deployment's images by repository alone (`image: tendworks/sandbox-claude-code`); the worker fills in the pin. A template with an explicit tag keeps it.
- **`deploy/.env.example`** lists every variable the stack reads.

## Sandbox clean-up

- The worker removes sandboxes and session volumes of its installation that belong to no live task or open chat, on start and every 5 minutes, and logs each removal.
- Failed removals are logged and shown as the new `/status` component `sandbox-cleanup` until a later pass succeeds; the harness records a failed removal in the transcript instead of swallowing it.
- It removes only what carries both the installation label and an owner label, and only once it is 10 minutes old. Unlabelled sandboxes and session volumes from before v0.2.0 are never removed automatically (see "Before you update"). A pass that cannot read the live tasks removes nothing and is reported like a failed removal.

## New `/status` components

| Component | When |
| --- | --- |
| `sandbox-cleanup` | always (worker); unhealthy while removals fail |
| `<schema>-schema` | only after a failed migration (server or worker) |

## Operator tools and docs

- `scripts/setup-env.sh`: creates `deploy/.env`.
- `scripts/backup.sh` and `scripts/restore.sh`: one dated archive with the store dump, the engine's state and the transcripts; restore into a stack without data. **Archives are sensitive**: they hold chat content, run inputs and transcripts (no tokens). They are written with mode 600; encrypt copies off the host. Session volumes and `deploy/.env` are not included: after a restore without them, a run that was working continues with its step's agent starting a new session in an empty workspace, and an open chat continues with a new agent session, without its earlier conversation, in an empty workspace (operator guide, Backup and restore).
- Operator guide: install from a tag, own configuration, secrets, GitHub access check before the first real run, access from your devices through a TLS layer (Tailscale `tailscale serve` recommended, reverse proxy with your own domain as alternative, ADR 0020), update, backup and restore, clean-up and reset, troubleshooting, acceptance checklist.

## Not supported

Rootless Docker, ARM hosts, several hosts or Kubernetes, downgrades, TLS or OIDC inside the platform. Known gaps: operator guide, "Known gaps".

## For developers

- Run `scripts/setup-env.sh` once per checkout before `pnpm e2e`; CI does the same.
- `pnpm e2e` runs the stack on the fixture configuration (`tests/fixtures/config` layered on the starter).
