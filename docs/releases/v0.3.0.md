# Tendworks v0.3.0 – generic platform: workspaces, triggers, notifications

Milestone 3 (spec #71, ADR 0022–0025): one installation serves several repositories and use cases. Repositories and host directories are declared once as workspaces, trigger bindings start a workflow per workspace on a schedule or for new issues, notifications reach your phone through Pushover, and you talk with an agent about one workspace's contents. The platform itself knows no pull requests: agents open them and report them, and you merge in the forge. Follow [docs/operator-guide.md](../operator-guide.md).

## Installation

**v0.3.0 needs a fresh installation**: empty stores and a new configuration directory. Nothing is migrated, and no backup is restored into it.

1. Remove any running stack with all its data: operator guide, [Reset](../operator-guide.md#reset) (`docker compose -f deploy/compose.yaml down -v` plus the sandboxes, session volumes and the sandbox network).
2. Check out `v0.3.0` and [install](../operator-guide.md#install), with a configuration directory copied from `examples/config`.
3. The install builds the sandbox image `tendworks/sandbox-claude-code:0.85.1-2` (`--profile sandbox-images build`); it carries the git credential helper that git workspaces need.

## What you configure

| Kind | Folder | What it does |
| --- | --- | --- |
| `Workspace` | `workspaces/` | a repository (`git`: URL on any host, default branch, its own agent token as `credentials`, optionally exposed as e.g. `GH_TOKEN`) or a host directory (`directory`: a path under `TEND_WORKSPACE_ROOTS`, one agent session at a time), plus an optional workspace assistant (ADR 0022) |
| `TriggerBinding` | `triggers/` | a workflow, a trigger and a list of workspaces: one run per workspace and item, with the input `{ workspace, item }`; triggers `schedule` (cron in UTC or an interval) and `github-issues` (labels, state, interval, the issues token); an item starts one run per binding and workspace, once (ADR 0023) |
| `NotificationChannel` | `notifications/` | Pushover (`integration: pushover`, token and user key as platform secrets, optional priority -2 to 1) or `fake` (server log), for a selection of `approval.requested`, `run.failed` and `run.completed`; delivery status per channel (ADR 0025) |
| `Policy` | `policies/` | per action of a human step and workflow: `ask` or `allow`; the strictest applies, and without a policy the step asks (ADR 0024) |
| Workflow | `workflows/` | the human step `call: approval` with an action, a question, links and custom answers, each continuing or stopping the run (ADR 0024) |

Agent profiles carry no repository credentials; what is specific to a repository lives in the repository (`README`, `CLAUDE.md`, `AGENTS.md`). References to unknown workspaces, workflows or assistant profiles, directories outside the root and `github-issues` bindings over anything but git workspaces on github.com stop the server at start, naming the problem.

## What works

- **Workspaces.** Git checkouts with a generic credential helper in the sandbox image, on the branch the workflow chooses; directory workspaces bound into the sandbox read-write or read-only, strictly under the operator's root also after resolving links.
- **Trigger bindings over workspaces** with pluggable trigger sources (`packages/trigger-source-*`), deduplicated per binding, workspace and item. `tend trigger list` shows kind, workspaces, schedule, next execution and last check.
- **Pull requests as artifacts.** `develop-issue` ends when the developer has opened its pull request with the workspace's agent token and reported it; the run, its step and its notifications show it, and the Pushover message opens it with a tap. The platform merges nothing and holds no forge write token.
- **Human step and policies.** `call: approval` asks and waits, also across restarts; `tend approval list|get|answer` and the web UI show the question, links and answers.
- **Notifications** to every channel that selects the event, with the run's artifacts; `tend notification list` and the web UI show the delivery per channel, including the reason of a failed one.
- **Chats.** `tend chat` talks with the platform assistant `assistant`; `tend chat --workspace <name>` and the web UI's new chat dialog with a workspace's assistant (default profile `workspace-assistant`, no platform tools). Read-only by default: a git workspace's credential is used for the checkout only, a directory is mounted read-only; `write: true` works on `tendworks/chat-<id>`. `tend workspace list` (`GET /workspaces`) shows the workspaces and their assistants.

## Starter configuration

`examples/config`: agents `developer`, `assistant`, `workspace-assistant`; the git workspace `playground` with a read-only assistant; workflows `develop-issue`, `check-workspace`, `hello-developer`, `restart-developer`; the suspended bindings `playground-ready-for-agent` (`github-issues`) and `playground-nightly-check` (`schedule`, 02:00 UTC); the Pushover template `notifications/phone.yaml.example`, which does nothing until renamed. A fresh stack starts no run.

## Secrets

| Secret | Held by | For |
| --- | --- | --- |
| an agent token per workspace, e.g. `TENDWORKS_AGENT_GITHUB_TOKEN` | worker, the sandboxes of that workspace's tasks | git and `gh` in that workspace: push branches, open pull requests |
| `TENDWORKS_PLATFORM_GITHUB_TOKEN` (issues token) | server | the `github-issues` trigger: read issues |
| `TENDWORKS_PLATFORM_PUSHOVER_TOKEN`, `TENDWORKS_PLATFORM_PUSHOVER_USER` | server | Pushover channels |

Exactly two GitHub tokens, both fine-grained: [docs/github-agent-access.md](../github-agent-access.md).

## Settings

| Variable | Meaning |
| --- | --- |
| `TEND_WORKSPACE_ROOTS` | absolute host directory that directory workspaces must lie under; mounted read-only into server and worker. Unset: no directory workspaces. The compose stack supports one root |

## Known gaps

- An agent in a workflow always holds its workspace's agent token; only a workspace assistant with `write: false` works without one.
- The issue trigger reads github.com only.
- A failed notification delivery is not retried; approval request messages carry no link.
- Not covered end to end (harness tests only): a workspace assistant with `write: true`, a read-only chat on a directory workspace.
- Operator guide, "Known gaps", for the rest.

## For developers

- Trigger sources implement `@tendworks/trigger-gateway/source` and are registered in `apps/server/src/trigger-sources.ts`; the dependency-cruiser rule `trigger-sources-use-only-the-port` keeps them apart from the domains.
- New ports and implementations in the port fitness function: `Workspace` (git, directory, empty), `TriggerSource` (schedule, github-issues, fake), `NotificationDelivery` (fake, Pushover).
- `pnpm e2e` rebuilds `tendworks/sandbox-scripted-acp:test`, which now carries git, a bare repository and the prompts `workspace:`, `write:` and `push:`.
