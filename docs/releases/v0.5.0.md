# Tendworks v0.5.0 – workflows started by hand (draft)

Draft notes for the next release, filled in as its changes land. Spec #130 (ADR 0028): a trigger binding of kind `manual` declares a workflow you start only when you decide, such as a review or a release, with the workspaces it may run in. Follow [docs/operator-guide.md](../operator-guide.md#manual). Spec #146 (ADR 0029): a workspace assistant's chat can work on a branch you choose ([Workspace assistants](../operator-guide.md#workspace-assistants)).

## Before you update

- No migration and no change to existing configuration: `schedule` and `github-issues` bindings work as before. A binding without `spec.input` starts its runs with the same input as before. Chats started without `branch` work on the same branch as before.

## What changed

| Area | Change |
| --- | --- |
| `TriggerBinding` | new trigger kind `manual: {}`: never fires on its own. The manual trigger source is deployed with the server. |
| Firing | `POST /triggers/{name}/fire` (API token; optional body `{ "workspace": "<name>" }`) starts one run per workspace of the binding, or only in the named one, with the input `{ ...spec.input, workspace, item }`, the binding as the run's origin, `trigger.fired`, and the firing recorded as the binding's last check. Each firing is a new item (`started by hand`, keyed by its time). Refused: `404` unknown binding, `409` suspended or not of kind `manual`, `400` a workspace that is not the binding's, `403` with the read-only token. `tend trigger fire <binding> [--workspace <name>] [--follow]` fires from the terminal and prints the started runs; `--follow` streams the run when exactly one starts. The web UI's Triggers page shows scheduled and manual bindings in two panels, "Scheduled" (with the timeline) and "By hand" (workflow, workspaces, last start), and Start on every manual binding (with the API token; disabled when suspended); over several workspaces it asks which of them, all preselected, and it opens the run when one started, else Runs. The overview has a Start panel with the same Start on every manual binding (left out without manual bindings and for the read-only token) that always asks first; its "Next trigger checks" lists only scheduled bindings. |
| `spec.input` | every `TriggerBinding`, of any kind, may carry a fixed `spec.input` object; each run it starts gets `{ ...spec.input, workspace, item }`, so one workflow serves several bindings. A binding whose `spec.input` sets `workspace` or `item` stops the server at start, with the reason in the log. |
| Starter configuration | new workflow `review-workspace` (the developer reviews a workspace read-only with the `focus` of its input and reports) and two manual bindings over `playground`: `playground-architecture-review` (`focus: architecture`) and `playground-security-review` (`focus: security`). They start nothing until you fire them; copy them into your configuration if you want them. |
| Trigger list | `schedule` and `nextExecutionAt` are optional in `GET /triggers`; a manual binding has neither. `tend trigger list` shows `-` for both; the web UI's Triggers page lists manual bindings in their own "By hand" panel, without schedule or next check. |
| Chats on a chosen branch | `POST /chats` takes an optional `branch` with `workspace`: a writing assistant's chat works on it when it starts with one of the workspace's new `assistant.branchPrefixes` (default none), continuing the branch when the remote has it and starting it from the default branch otherwise. The chat keeps its branch (new `branch` on the chat, also `tendworks/chat-<id>` for a writing chat started without one) and checks it out again when it resumes. A read-only assistant's chat may check out any branch the remote has, e.g. a workflow's issue branch for a review, regardless of the prefixes; it never creates one, so a branch the remote does not have fails the chat with git's reason (likewise a workflow task with `write: false`). Refused with `400 Branch not allowed` and the reason: no listed prefix or the default branch (writing chats), an invalid name, a directory workspace; `400 Invalid request` for `branch` with `agent`. `GET /workspaces` shows each assistant's `branchPrefixes`. |
| Contracts | `startChatRequest.branch` and `chat.branch` in `contracts/schemas/chat.schema.yaml`, `workspaceAssistant.branchPrefixes` in `contracts/schemas/workspace.schema.yaml`, `branchPrefixes` on the assistant in `GET /workspaces`. `manualTrigger` and `spec.input` (`TriggerBindingInput`) in `contracts/schemas/trigger-binding.schema.yaml`; `fireRequest` and `fireResult` in `contracts/schemas/trigger.schema.yaml`; `POST /triggers/{name}/fire` in the control plane and trigger gateway APIs. |

## What you configure

1. Optionally add a binding with `trigger: { manual: {} }` to `triggers/` ([`manual`](../operator-guide.md#manual)), then `docker compose -f deploy/compose.yaml restart server`.
2. Fire it: `tend trigger fire <binding>`, or Start on the binding on the web UI's overview or Triggers page.
3. Optionally give a binding a fixed `spec.input` ([Trigger bindings](../operator-guide.md#trigger-bindings)), e.g. the starter's review bindings with `focus`.
4. Optionally let a writing workspace assistant work on named branches: `branchPrefixes: [prototype/]` under `spec.assistant` ([Workspace assistants](../operator-guide.md#workspace-assistants)), then restart server and worker. Protect the default branch and release branches through the repository's rules: the workspace's token reaches every branch it can push to.

## Known gaps

- Who fired a binding is not recorded; there is one shared API token until OIDC.
- `schedule` and `github-issues` bindings cannot be fired by hand.
